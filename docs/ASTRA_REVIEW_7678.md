### F-abort-tail — OPEN Medium residual of cancellation integrity

The new conservative parser never sees an unterminated tail: `_open_journal` first invokes `_set_aside_tail` (`hive/reducer.py:359`), preserves it in a durable aside, and truncates it out of the input. This permits a particularly small cancelled-entry revival:

```text
write genuine uncertain rebind X + fence
clear_journal_fence(...) -> True; durable abort(X); marker removed
intact fresh replay -> held (cancellation confirmed)
delete ONLY the final newline byte of the journal
# abort JSON remains complete and its self-hash is unchanged
fresh reducer copies abort(X) into .torn-* and removes it from journal
full original event replay -> X applies; owner(p)=i; i closes
corrupt_records=[]; indeterminate=None; second fresh replay also applies X
```

`followup7678.json.torn_cancelled_record` records original/damaged bytes, exact aside bytes and both restarts. A truncated abort-JSON tail has the same effect. The control with the same malformed abort **terminated by a newline** correctly flags corruption and blocks the earlier entry. Replacing the cancellation line with whitespace is an additional, broader destructive-content control: `if not raw.strip()` skips it and the cancelled operation replays. No hashes are recomputed.

This is not the old torn-fragment forensic-data-loss bug: the aside contains all removed bytes. It is **authorization loss by treating a possibly cancelling tail as harmless**. The single-newline witness neither reorders records nor requires the compound I/O failure above. **Required closure:** unknown/cancellation tail disposition must conservatively block possible targets and remain effective across subsequent restarts; preserving the bytes in an unconsulted aside is insufficient. A safely authenticated complete cancellation tail could alternatively be recognized, but malformed tails still need a fail-closed disposition. Medium reflects storage corruption, not hostile-store forgery.

### F-abort-order-scope — OPEN Medium under reordered storage; intact-order controls pass

The new `n < last_bad` policy (`hive/reducer.py:689`) protects only records physically before the last unverified record. The independent temporal fixtures use **authentic writer-produced rebind/cancellation records**, preserving their hashes and event streams:

| Physical sequence | Observed replay | Assessment |
|---|---|---|
| A, corrupt cancellation(A), later successful B | B only | Safe for original serial append order; A stays cancelled |
| A, B, corrupt cancellation(B) | Neither | Conservative and safe |
| A, cancellation(B), B | B | Cancellation is diagnosed as naming no earlier rebind, but its later target revives |
| A, corrupt cancellation(B), B | B | Same revival after one extra ID-character edit; hash mismatch visible |
| B, corrupt cancellation(B), duplicate B | Neither | Earlier seen-ID deduplication does not let duplicate B escape |
| A, cancellation(A), B, corrupt cancellation(B) | Neither | Intact-order interleaved cancellations stay safe |

The forward fixtures move a genuine cancellation before its target; they do **not** arise from the current intact single-writer append protocol. In the order-preserving, in-place-edit model, a cancellation can only concern an earlier entry, so the author's narrower rule is defensible and the retained serial/interleaved controls prove the intended availability benefit. It is **not** safe against record displacement/reordering: both forward fixtures revive the original explicitly cancelled B, with `corrupt_records` present, over two restarts. A valid hash is not a physical-order binding, and no journal chain enforces the assumed order.

Severity is **Medium with that stronger storage-corruption precondition**, not a claim that a normal new rebind after an earlier corrupt cancellation is inherently unsafe. **Required closure for broad corruption protection:** fence the whole journal when target/order cannot be trusted, or enforce/verifiably bind journal ordering. If deliberately supporting only order-preserving corruption, make that assumption and operational exclusion explicit; do not represent `corrupt_records` alone as a universal fail-closed guarantee. The gate is already blocked by the newline and compound-refusal witnesses independent of this scope judgment.
