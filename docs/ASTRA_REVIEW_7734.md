## 2. F-reset-intent-durability-status — still OPEN Medium

**Corrected original witnesses.** The adapted, provenance-recorded [7727 intent harness](../experiments/20261008-astra-7734/intent_final7727.py) reruns both: (1) error immediately after intent creation with **zero fsyncs**, and (2) intent fsync EIO plus cleanup unlink EACCES. Both now report `intent_durable: false` and preserve the old pair. The first still demonstrates, under the explicitly labeled loss-of-unsynced-marker model, that the old authorization can return. That is why the accurate keep-service-stopped/retry instruction matters. This is not an ordinary-startup marker bypass or a physical power-loss measurement.

**Remaining defect.** `_sync_existing_durably()` at `hive/reducer.py:450` asks `os.path.isfile(path)`. Python's predicate catches OSError and returns False. It does not distinguish a positively identified nonregular entry from a regular file whose metadata could not be read. Consequently a transient EIO or EACCES during classification of an existing regular marker skips `os.open` and file fsync entirely, executes only `_fsync_dir`, returns successfully, and sets `established = True`.

Two independent errno variants in `intent7734.json → classification_errors` reproduce this using a real, newly written, un-fsync'd regular intent. Inject EIO or EACCES only into that helper's `stat()`; let directory fsync succeed; inject a separate EIO at the first old-journal rename to expose the recovery result. The recorded fsync list contains **only the parent directory**, yet both fence and `journal_resets` report **`intent_durable: true`**, and the error says **“file and directory fsync confirmed”** and **“every start fences”**. The original pair remains byte-identical in these witnesses. Control lstat errors on regular markers do not skip the file fsync and are separately recorded.

This violates the requested and documented two-fsync gate, even though the directory was synced. The evidence does **not** demonstrate actual marker loss after that directory fsync or assert that every filesystem permits that loss; it demonstrates that the promised file durability operation was skipped following an I/O error. The helper's own “Raises OSError if any step fails” statement at `:449` is false for classification failures. A successful overall reset might still finish safely; the failure/recovery durability assurance is what remains unqualified.

**Required correction:** use error-propagating metadata classification (for example, explicit `lstat` plus type checks), and do not set confirmation after an unknown type/readability result. For regular files, require successful file and directory synchronization. Retain safe in-memory discard and old-pair-before-confirmation ordering. Rerun these metadata errors as well as the existing witnesses and intent boundaries.

The helper intentionally supports symlink/directory namespace-only markers (`:447`); the separate metadata controls confirm that they receive directory-only fsync yet the error still says “file and directory fsync confirmed.” Startup only needs their entry to block, so this is not independently presented as a replay failure. Either explicitly document and accurately describe that type-specific guarantee or reject these entries conservatively. The policy `docs/POLICY_MULTI_PLAN_SUPERSESSION.md:150` and `README.md:107` currently promise both fsyncs without that exception.

## 3. Presence reporting, leftover markers and recovery guidance

**F-reset-error-metadata-status — OPEN Low.** At `hive/reducer.py:1103`, `os.path.lexists(ip)` likewise turns an lstat I/O error into False. The error handler then reasons from “not observable” as though it had proved absence. [metadata7734.json](../experiments/20261008-astra-7734/metadata7734.json) records two compound failures:

1. Establish the intent durably and successfully move the old journal aside. Fail reading the old anchor, then make the handler's marker lstat fail with EIO. The marker actually remains, but `intent_present` is False and the text claims **“The old journal and .id are unchanged on disk (at most a marker was written)”**. The old journal path has already been moved: that claim is false.
2. Finish the new pair, fail intent unlink with EACCES, and make that handler's lstat fail with EIO. The still-present marker is reported absent, and the text says **“the marker was unlinked.”** The restart-safe conclusion is nevertheless correct because the new pair is complete; an ordinary restart actually fences on the surviving marker.

Both live reducers remain fenced with no pending rebind; normal restarts with metadata reads restored are fenced. This is **Low**, not a demonstrated authorization resurrection. Preserve the original error and represent presence-inspection failure conservatively (unknown/error or separately recorded status); do not infer unchanged pair or successful unlink solely from an unavailable namespace observation. The step and completed operations should determine the recovery explanation.

Outside this metadata-error branch, the requested status/text checks pass. Failed-reset entries expose `intent_present` and `intent_durable` consistently in fence and audit; successful reset entries have neither field and no failure fence (the new fields are failure diagnostics, not a reconstructed durable history). The revised policy correctly distinguishes **old pair unchanged** from **nothing changed on disk** for failures before confirmation: an empty/partial marker can already exist.

Mode-000 behavior is independently exercised under non-root **uid 1001**: confirmation raises PermissionError, reports not durable/present, does not delete or chmod the marker, and leaves the old pair identical. The harness then repairs permissions (also allowing evidence hashing) and successfully retries; held replay remains held. Policy `:159` accurately instructs fixing permissions, **not deleting the marker**, and retrying. The retained 42 startup controls include empty, partial, damaged, mode-000, directory and dangling-link intents crossed with seven pair/artifact states. Clearance is still zero-carry; a directory obstruction remains fenced and requires operator correction rather than a promise that generic retry repairs it.
